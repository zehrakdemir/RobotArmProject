# Durum notu — 2026-09-08 sonu

## TEST EDİLMEYİ BEKLEYEN DEĞİŞİKLİK (yarın ilk iş)

`fairino_hardware_interface.cpp` içinde **comType=1 (UDP, robot portu 20007)** değişikliği
yapıldı, derlendi ve kuruldu **ama canlı robotta HİÇ test edilmedi.**

`fairino_launch` açılışında şu satır beklenir:

```
Servo akisi UDP (comType=1, port 20007) uzerinden baslatildi.
```

Çıkmazsa (firmware desteklemiyorsa) otomatik olarak XML-RPC'ye döner ve onu loglar —
bu durumda bugünkü duruma göre kötüleşme olmaz.

## Günün asıl bulgusu

Sürücü, 100Hz'lik servo akışını **XML-RPC (HTTP+XML)** üzerinden gönderiyordu.
SDK başlığı (`libfairino/include/robot.h`) bunun için ayrı bir kanal tanımlıyor:

```
@param [in] comType 指令下发类型；0-xmlrpc；1-UDP(对应机器人20007端口)
```

Bu neden önemli:
- Her ServoJ = bir HTTP istek/yanıt + XML ayrıştırma → `write()` ağa takılıyor
- SDK'nın önerdiği `cmdT` aralığı 1–1.6ms (625–1000Hz) — XML-RPC ile imkânsız,
  o parametre UDP için tasarlanmış
- Kendiliğinden gelen `err=-2` (ERR_SOCKET_COM_FAILED) = kopan şey port 20003'ün
  TCP bağlantısı, yani XML-RPC kanalı. UDP'de kopacak bağlantı yok.

## Hata kodları (libfairino/include/robot_error.h)

| Kod | Anlam |
|---|---|
| `-2` | ERR_SOCKET_COM_FAILED — ağ iletişim hatası (komut robota ULAŞMIYOR) |
| `14` | ERR_EXECUTION_FAILED — robot komutu reddediyor (genelde faultlu) |
| `29` | ERR_SERVOJ_JOINT_OVERRUN — eklem değeri limit dışı |
| `30` | Sıfırlanamaz arıza → kontrol kutusunu kapat-aç |

## Bugün yapılan ve KALICI olan diğer düzeltmeler

1. **RT önceliği** (`auto_fairino_launch.sh`): ros2_control `Could not enable FIFO RT
   scheduling policy` uyarısı veriyordu → döngü düzensizleşiyordu. İzin makinede zaten
   tanımlıymış (`/etc/security/limits.d/99-realtime.conf`, kullanıcı `realtime` grubunda)
   ama WSL tam PAM login yapmadığı için uygulanmıyordu (`ulimit -r`=0).
   Launch artık `sudo -n -E -u $USER` üzerinden başlıyor → rtprio 99.
   **Sonuç: doğrulandı**, periyotlar 0.003–0.017 zıplamasından kararlı 0.01000'e geçti.

2. **Hız sınırlayıcı (slew limiter)**: bir gönderimdeki pozisyon değişimi güvenli hızın
   (limitin ~%60'ı ≈ 108°/sn) cmdT süresinde kat edeceğini aşamaz. Normal çalışmada
   (%10 hızda ~16°/sn) devreye girmez. Devreye girerse `SINIRLAYICI devrede` diye loglar.

3. **cmdT** artık gerçek ölçülen periyot, dokümante edilen 1–16ms aralığına kırpılmış.

4. **Seyreltme KALDIRILDI** — 8ms altı komutları atlamak hareketi sıçramalı yapıyordu.

5. **Otomatik toparlama BİLEREK YOK** — servo akışı koptuğunda sürücü kendiliğinden
   `ServoMoveStart` çağırmıyor (güvenlik: manuel modda robot elle oynatılmış olabilir,
   JTC'nin hedefi eski pozisyon → operatörün elleri üstündeyken robot kendiliğinden
   hareket edebilirdi). Bunun yerine tek seferlik `SERVO AKISI KOPTU` hatası basıyor.
   Güvenli toparlama yolu: WebApp'ten Clear → `clearfault` (deactivate/activate yapar,
   komut pozisyonunu gerçek pozisyona senkronlar).

6. **movecobot.py**: `__init__` içine aşama aşama zaman damgalı ilerleme logları eklendi
   (`[+X.Xs] ...`) — MoveItPy kurulumu doğası gereği yavaş, önceden hiç çıktı vermediği
   için "donmuş" sanılıyordu.

7. **movecobot.py**: hareket sonrası doğrulama artık robotun gerçek fault kodunu
   (`robot_state_pkg.main_code/sub_code`) kontrol edip raporluyor. Önceki "hedeften
   135.9 derece uzakta" mesajı yanıltıcıydı — o sapma gerçek değildi, fault sonrası
   okunan sıfır/placeholder değerden geliyordu.

## Test edilip ÇÜRÜTÜLEN teoriler (tekrar denemeye gerek yok)

  → İki ayrı süreçten eşzamanlı bağlantı testi: **0/36 hata**. Çürütüldü.

  döndüğü için ağ beklemesi olmuyor ve döngü hızlanıyor. Patlama sonuç, sebep değil.
